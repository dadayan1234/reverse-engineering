# Implementation plan

1. **Repository and workflow.** Keep one ESP-IDF C application in `src/` with canonical markers in `include/`; use `platformio.ini` as the Windows/VS Code entry point. Put host scripts in `scripts/`, synthetic-only tests in `tests/`, immutable per-run evidence in `evidence/`, and derived comparisons in `results/`.
2. **Build and scenarios.** Map `baseline`, `secure_boot`, `flash_encryption`, and `full_security` to the fixed A–D IDs. Give each environment its own `sdkconfig` path and versioned defaults. ESP-IDF config and device state alone control security; application source is shared. Archive resolved configs, binaries, maps, logs, hashes, commit, and tool versions per build. Secure configurations remain preparation targets until their exact installed framework options and provisioning procedure are verified.
3. **N16R8 validation.** Start from PlatformIO's generic ESP32-S3 board, set 16 MB build assumptions explicitly, then gate hardware use on observed chip/revision, COM port, flash ID/capacity, practical PSRAM evidence, and eFuse state. Record actual board markings and wiring; do not infer hardware from the board manifest.
4. **Firmware.** Initialize NVS and Wi-Fi, attempt connection with the synthetic seed markers, use the API/static markers locally, optionally write the NVS marker, report non-secret status, and heartbeat. No scenario-specific application branches.
5. **Evidence.** A shared logger creates unique run directories and timestamped manifest, events, audit, and command records. All important commands capture arguments, cwd, times, exit status, stdout, and stderr. Preserve failed attempts and partial files; never overwrite raw evidence.
6. **Acquisition and analysis.** Preflight and eFuse capture precede a version-compatible `esptool` raw read with validated flash size. Hash every acquired file immediately. Python analysis computes size/hash, byte distribution and entropy, exact ASCII marker offsets, erased/zero-heavy regions, and structural partition/image findings from acquired bytes; label build-derived offsets separately. Aggregate only observed fields from run manifests and analysis.
7. **Provisioning boundary.** Generate plans for B–D and capture before/after state, but make no automatic eFuse burns or irreversible interface changes. Require a separate explicit operator action for any later destructive script; record Flash Encryption Development/Release mode.
8. **Verification and order.** Implement baseline build/evidence/analysis first, test logger, hashing, scanner, entropy, manifest, overwrite, partial read, aggregation, and destructive gate with synthetic fixtures, then prepare B–D configs. Validate a real baseline build, flash, boot, preflight, acquisition, and recovery only when the N16R8 board and COM port are available. Document exact Windows commands and unresolved hardware observations.
